# PIXEL backend release checks

The backend workflow uses a disposable PostgreSQL database with pgvector. It checks Git history for secrets and verifies the lockfile, published dependency advisories, backend lint and tests, migrations, production settings and Admin static files. Require the Backend checks job on the release branch before deployment. CI uses synthetic credentials and has read-only repository access.

For hosting, set `DJANGO_DEBUG=false`, generate a new random `DJANGO_SECRET_KEY`, and supply explicit HTTPS frontend, API and CORS origins. Use same-site hostnames, such as `app.example.org` and `api.example.org`, for browser cookies. Set the exact API hostname in `DJANGO_ALLOWED_HOSTS`. Configure SMTP over TLS, PostgreSQL over TLS and a shared Redis cache via `PIXEL_CACHE_URL`. Use `rediss://` for remote Redis. Pass credentials through the host's secret store. Use separate migration and runtime PostgreSQL credentials, set the runtime role to the minimum database privileges, and use a pooled runtime URL.

Only enable `DJANGO_TRUST_HTTPS_PROXY` when the host overwrites forwarded protocol headers and blocks direct access to the backend. Configure `DJANGO_TRUSTED_PROXY_COUNT` only for a known ingress chain that sanitizes forwarded client addresses. HSTS subdomains and preload are separate opt-in deployment decisions. Django may warn about either when disabled. Review the real environment with `python manage.py check --deploy` before release.

Run `python manage.py collectstatic --noinput` during the build. On Linux, begin with `gunicorn config.wsgi:application --worker-class gthread --workers 2 --threads 4` from `backend/` and size it to the host. Run migrations once before starting the web process. Run gallery sync and the face worker as separate processes. The API and its face worker need access to the same private non-public storage for temporary selfie files and the same `FACE_WORKER_NODE_ID`. Allow face-search expiry and cleanup to run continuously. Keep application access logs free of signed media URLs and OAuth query strings. Limit request rates and upload bodies at the ingress, with a deliberate allowance for approved admin gallery batches.

Protect the existing admin account with a unique password and MFA on its identity provider. Staging acceptance should exercise a member and an admin in separate sessions, logout and revocation, draft access, signed media expiry, Drive sync, OAuth callbacks, and the host's block on arbitrary inbound traffic to the application processes. Audit access logs and verify a Neon restore before inviting users. Test with synthetic data and credentials.

For the 100-user acceptance test, populate a staging database with representative events and discussions. Issue one fresh access token per onboarded staging member and put the 100 tokens in an ignored local JSON file. Run `uv run python check_capacity.py https://api.staging.example.org .local/staging-tokens.json` from `backend/`. The metadata smoke test requires zero failed requests and a p95 of at most one second. Repeat after a cold start. Then separately test the expected mix of photo/video streams, uploads, writes and face-search jobs, and inspect memory, worker saturation, database connections, Drive quota and ingress bandwidth. A passing metadata test alone does not establish full workload capacity. Keep the staging token file private and revoke the sessions after testing.
