# Authentication and onboarding

Implemented 18 November 2026. This supersedes the earlier planning-only account status. Local Django authentication is connected to the existing Expo frontend; production deployment and later content/recognition phases remain pending.

## Try it

Start Django using `backend/README.md`, then run `npm run web` from `frontend/` and open `http://localhost:8081/`. Main administrator: **Pixel / pixel.club@sait.ac.in**. The generated initial password is stored privately in `backend/.local/admin-initial-password.txt`, not in source. Existing layouts, glass effects and theme are preserved; new forms use the existing palette, typography and outlined/offset buttons.

First login: current privacy/terms checkboxes → sign in → choose username → profile details → five-section tour. Later logins resume unfinished steps and never repeat a completed tour. Profile editing uses a small pencil beside the name; there is no tour replay button. **Logout replaces the profile header inbox icon**; other sections retain notifications. Logout revokes the server session immediately and returns to sign-in.

## Account rules

- Only exact `@sait.ac.in` addresses pass server validation. Gmail, lookalike suffixes and subdomains are rejected.
- Password signup requires mailbox verification before login. Verification links contain random tokens stored as hashes, expire in 30 minutes and work once. The verification page sets the final password, preventing an unverified account preclaim from preserving an attacker's password.
- Login accepts college email, username, or `@username`, case-insensitively. Passwords are case-sensitive, with Django validation, a 12-character minimum and a 128-character input limit.
- Usernames use 3–30 lowercase ASCII letters, numbers, periods or underscores, include a letter, and cannot have first/last/consecutive periods. Uniqueness is case-insensitive; official names are reserved for Administrators. Later username changes are administrator-managed.
- Public signup/profile payloads reject unknown or privileged fields. New members start as Students; Faculty approval is administrator-controlled. Exactly Administrator, Faculty and Student are supported.
- Active verified Administrators with staff access alone can enter Django Admin or management endpoints. Public signup cannot claim the reserved main administrator email. Provision administrators with the local trusted command.

## Google configuration

Use a **Web application** OAuth client in [Google Auth Platform → Clients](https://console.cloud.google.com/auth/clients). This is a confidential server flow; no Google secret goes into the mobile app.

Register this exact development redirect URI:

```text
http://localhost:8000/api/v1/auth/google/callback/
```

Save both settings in **backend/.env**, keeping its existing Django secret:

```env
GOOGLE_CLIENT_ID=your-client-id
GOOGLE_CLIENT_SECRET=your-private-client-secret
```

Restart Django and refresh the app. Until both are present, Google setup is labelled pending. Configure Branding and Audience; Internal is appropriate only when this project belongs to the college's Google Workspace organization. Otherwise use External testing with permitted college test users. Backend checks still enforce verified email, `hd=sait.ac.in`, issuer, audience, signature and nonce.

Google reveals the full secret at creation. Save it privately or use **Add Secret** on the client details page if the original is lost. [Google's client management guide](https://support.google.com/cloud/answer/15549257?hl=en) covers creation and rotation. Do not store secrets in `.env.example`, `EXPO_PUBLIC_*`, frontend code or GitHub.

### Start sign-in from PIXEL

The Google callback URL is a return destination, not a page to open manually.
Start at `http://localhost:8081/`, accept the policy checkboxes and choose
**Continue with Google**. Google must return a fresh authorization code and the
matching state generated by that request. Direct, incomplete or expired browser
callback visits now lead to a themed recovery screen with **Back to sign in**.
Machine callers still receive HTTP 400, and invalid callbacks cannot create a
login session. Browser recovery and rejection of expired state are regression-tested.

Provider state/nonce/PKCE protect the Google flow. A second app verifier binds the returned one-time ticket to the initiating app/tab. Only that ticket is sent to the fixed app callback; JWTs are not placed in URLs. Tickets expire in two minutes and cannot be replayed. The native callback is `pixelmobile://auth/callback`, browser callback `http://localhost:8081/auth/callback`; arbitrary caller-supplied redirects are rejected. Verified Google sign-in never elevates roles and discards unverified pre-existing passwords.

Google adapter/failure paths are covered by mocked provider tests. A live college OAuth roundtrip needs the actual project/credentials and has not been claimed as passed.

## Email verification and deferred reset

Development emails are written to **backend/.local/emails/**. Open the newest message locally, follow the verification link and choose/confirm the final password. This does not deliver to actual college inboxes. Keep those links private.

For real delivery, set `EMAIL_BACKEND=django.core.mail.backends.smtp.EmailBackend` and configure `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_USE_TLS`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD` and `DEFAULT_FROM_EMAIL` in the private backend environment. Use an approved sender/provider.

Password reset is disabled by request. Its login link explains that it is not yet available; there is no reset endpoint or false email-sent message.

## API

Paths below are under `/api/v1/`. Protected endpoints require a Bearer access token.

| Endpoint | Purpose |
| --- | --- |
| `GET auth/config/` | Policies/versions, domain, Google/reset availability and browser CSRF token |
| `POST auth/register/` | College email/password and current policy acknowledgements |
| `POST auth/resend-verification/` | Generic response; delivers only for an eligible unverified account |
| `POST auth/verify/` | Consume verification token and set final password |
| `POST auth/login/` | Identifier/password, client type and policy acknowledgements |
| `POST auth/refresh/` | Rotate refresh credential and return a new access token |
| `POST auth/logout/` | Revoke active session and clear browser refresh cookie |
| `POST auth/google/start/` | Begin provider flow using policies and app challenge |
| `GET auth/google/callback/` | Validate provider identity and return one-time app ticket |
| `POST auth/google/exchange/` | Redeem ticket with matching verifier/client |
| `GET me/` | Private profile and onboarding state |
| `POST me/username/` | Claim username once |
| `PUT me/profile/` | Update whitelisted profile fields after username selection |
| `POST me/tour/` | Persist tour completion |
| `GET users/?q=...` | Search up to 20 verified onboarded college profiles |
| `GET users/<username>/` | College-visible profile, excluding email/security flags |
| `GET moments/` | Paginated administrator-published video records |
| `GET management/status/` | Administrator-only dashboard access check |

## Sessions and privacy

Access tokens expire in five minutes; server sessions have an absolute seven-day expiry. Refresh credentials rotate and old credentials cannot be replayed. Protected calls also check active/verified membership, password changes and server revocation, so logout and administrator password changes invalidate existing credentials immediately.

Native refresh tokens use SecureStore. Browser refresh credentials stay in HttpOnly SameSite=Lax cookies; browser access tokens are memory-only. Browser login, refresh and Google exchange require CSRF protection. Browser sessionStorage holds only a temporary OAuth verifier, never session tokens.

Policy acknowledgements are versioned server records. The policy explicitly separates account acceptance from biometric consent. Find Yourself currently captures no selfie and produces no invented matches. Public profiles omit email and security fields. Audit metadata excludes sensitive payloads, and Django's development access logger redacts Google callback queries. Configure equivalent proxy/access-log redaction in production.

Before public release: obtain college approval for notices/terms, configure SMTP/HTTPS/PostgreSQL, choose same-site API/frontend hosting or review cookie strategy, configure a shared throttle cache and infrastructure abuse controls, run cleanup daily and test backups. Local throttle cache is per process, not a distributed security boundary. Hash-keyed account limits supplement IP limits to accommodate campus NAT.
